# 模块十：事件与日志 (Events & System Logs)

## 功能说明

主导航「事件与日志」统一承载两类排查信息，页面内以标签页切换：

| 标签页 | 内容 | 数据源 |
|--------|------|--------|
| 🔔 事件与告警 | 结构化系统事件：严重度 / 时间范围 / 状态（未读 / 已读未解决 / 已解决）筛选、分页、单条已读或解决、按当前筛选批量确认/批量解决、失败投递重新入队 | `system_event_log`（`GET /api/system/events`） |
| 📋 系统日志 | 应用程序运行日志的实时查看、级别控制与日志文件列表 | `app.log` / `access.log` 等文本文件 |

事件与告警列表与仪表盘「事件与告警」卡片的弹窗共用同一套筛选与批量操作逻辑（`events_center.js` 的 `_eventsToolbarHtml` / `_loadEventsPanel` / `eventsAckCurrent` / `eventsResolveCurrent`），避免两处口径漂移。仪表盘卡片的数字仍可点击弹窗快速查看。

### 事件生命周期（open → acked → resolved）

「已读」不等于「已解决」：`acked_at` 只表示人看过，`resolved_at` 才表示问题消失。状态由两列派生，不单独存储：

| 状态 | 条件 | 含义 |
|------|------|------|
| `open` | `acked_at IS NULL AND resolved_at IS NULL` | 未读，需要关注 |
| `acked` | `acked_at IS NOT NULL AND resolved_at IS NULL` | 已读，但问题可能仍在 |
| `resolved` | `resolved_at IS NOT NULL` | 已解决（同时视为已读） |

**自愈事件自动解决**：站点恢复时（`site_monitor.run_check` 探测成功）自动 resolve 对应 `site_unavailable`；数据库写锁探针（`nsfocus_db_health`，每 10 分钟）恢复后自动 resolve `log_error` 中 `error_type=DB错误` 的事件，`resolved_by='auto'`。探针与正常写共用进程写队列：先等队列（3 秒），拿到后再用独立的 3 秒 `busy_timeout` 探测 `BEGIN IMMEDIATE`，排队时间不计入锁等待；队列一直繁忙时判定为 `skipped`，不告警也不 resolve。人工操作记录为 `user:<id>`。

**未读口径**：CRITICAL / ERROR / WARNING 且 `acked_at IS NULL AND resolved_at IS NULL`。已解决事件不再计入未读，但仍保留在列表中可追溯。

**保留期**：每日 03:00 数据库清理时删除过期事件——已解决 / INFO 180 天，未解决告警 365 天（`cleanup_old_events`）。

### 批量确认 / 批量解决

「批量确认」只标记当前筛选条件下的未读事件：`POST /api/system/events/ack-all` 接收 `severity`（空 = 全部严重度）与 `since_hours`（0 = 全部时间），SQL 只更新 `acked_at IS NULL AND resolved_at IS NULL` 且落在该范围的行；已读、已解决与筛选范围外的事件不受影响。

「批量解决」只标记当前筛选条件下的未解决事件：`POST /api/system/events/resolve-all` 接收相同的 `severity` / `since_hours`（另支持 `event_type`），只更新 `resolved_at IS NULL` 的行，并同时补写 `acked_at`。单条操作使用 `POST /api/system/events/<id>/ack` 与 `POST /api/system/events/<id>/resolve`。

## 系统日志

### 日志文件

| 文件 | 说明 |
|------|------|
| `logs/app.log` | 主应用日志（INFO/WARNING/ERROR/DEBUG） |
| `logs/access.log` | Web 访问日志 |
| `logs/audit.log` | 操作审计日志（用户操作记录） |
| `logs/discover.log` | 产品发现日志 |
| `logs/heartbeat.log` | Session 心跳探测日志 |

## 日志格式

app.log 示例：
```
2026-06-12 10:00:00 [INFO] [scheduler] 采集任务开始
2026-06-12 10:00:05 [WARNING] [collector] 连接超时: update.nsfocus.com
2026-06-12 10:00:10 [ERROR] [collector] HTTPSConnectionPool: connection timeout
```

audit.log 示例：
```
2026-06-12T10:00:00 - [settings_update] user_id=1 ip=127.0.0.1 details={'keys': ['collect_interval']}
2026-06-12T10:05:00 - [subscription_create] user_id=1 ip=127.0.0.1 details={'id': 5, 'name': '客户A-WAF'}
```

## API 设计

### GET /api/system/log-files

列出日志文件（含大小、修改时间）。

**响应**：
```json
{
  "code": 0,
  "data": {
    "files": [
      {
        "name": "app.log",
        "size": 1048576,
        "size_human": "1.0MB",
        "modified": "2026-06-12T14:00:00"
      },
      {
        "name": "app.log.1",
        "size": 5242880,
        "size_human": "5.0MB",
        "modified": "2026-06-11T00:00:00"
      }
    ],
    "log_dir": "/root/nsfocus-monitor/logs"
  }
}
```

### GET /api/system/logs

查看日志内容（倒序分页）。

**查询参数**：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| file | "app.log" | 日志文件名 |
| lines | 200 | 行数（最大1000） |
| level | - | 过滤级别：DEBUG/INFO/WARNING/ERROR |

**响应**：
```json
{
  "code": 0,
  "data": {
    "file": "app.log",
    "lines": [
      "2026-06-12 14:00:00 [ERROR] [collector] ConnectTimeoutError: ...",
      "2026-06-12 13:55:00 [INFO] [scheduler] 采集完成，发现 3 个新包"
    ],
    "total": 200,
    "requested": 200,
    "level": "ERROR",
    "current_log_level": "INFO"
  }
}
```

## 审计日志（audit.log）

记录用户的关键操作：

| 操作 | 说明 |
|------|------|
| settings_update | 修改系统配置 |
| event_config_update | 修改事件通知配置 |
| subscription_create | 创建订阅规则 |
| subscription_delete | 删除订阅规则 |
| customer_delete | 删除客户（含保护逻辑） |
| history_clear | 清空推送历史 |
| force_stop_settings | 强制停止采集并保存配置 |

格式：`[操作] user_id=N ip=地址 details={详细信息}`

## 日志存储路径

通过环境变量配置：
- `MONITOR_LOG_DIR`：日志根目录（默认 `~/.local/share/nsfocus-monitor-data/logs`）
- Linux 默认：`/root/.local/share/nsfocus-monitor-data/logs/`
- Windows 默认：`%LOCALAPPDATA%\nsfocus-monitor-data\logs\`
