# 仪表盘（可观测性）

> 2026-11-11 起导航与页面标题统一叫「仪表盘」，内部路由/文件仍为 `observability`。

网页端把 `GET /api/metrics` 的运行指标直接可视化，不需要再手工调接口或看日志判断「投递是否健康、队列是否堵、采集是否及时」。

## 入口与刷新

- 登录后的默认首页，也是主导航第一项 **「仪表盘」**（`data-page="observability"`），同时提供「🔄 重启服务」入口。
- 默认窗口 **最近 24 小时**，可切换 6 小时 / 7 天 / 30 天；窗口影响投递、产品更新、事件与客户推送统计，队列、存储、调度任务始终是当前值。
- 客户推送与产品更新聚合跟随页面全局窗口，不再单独提供时间按钮；点击客户行按窗口天数下钻推送历史。
- 页面每 **30 秒**自动刷新；切到其他页面或退出登录时定时器立即停止，避免后台持续拉取。
- 手动「↻ 刷新」与自动刷新共用同一接口，不会重复叠加定时器。

## 时间口径（硬规则）

- **DB 一律存 UTC**：SQLite `datetime('now')`、Python `utc_now()` 或 naive UTC ISO 字符串，不写服务器本地时间。
- **只在这些边界转 UTC+8**：页面展示、静默期/推送窗口、汇总周期、月度报告、Prometheus「今日」口径。固定使用 `src/core/timeutil.py` 的 `cst_now()` / `cst_month_bounds()`，偏移恒为 +08:00，不依赖服务器 TZ，也不做夏令时。
- **队列时间**：`delayed_queue.push_after` / `pushed_at` / `next_attempt_at` / `last_attempt_at` 均为 UTC；旧版本写入的本地时间在启动时按服务器偏移一次性转换，并写 `system_settings.delayed_queue_timestamps_utc=1` 保证幂等。所有到期、退避、逾期统计都按 UTC 比较。
- **前端解析**：`serverTime()` / `fmtTZ()` 接受 naive UTC、`Z`、`+00:00`、`+08:00` 等形式；无时区后缀按 UTC 解析，输出统一为 UTC+8。不要再用字符串截断或浏览器本地时区。
- **测试**：`tests/test_time_conventions.py` 覆盖跨天、跨月、跨年、闰年 2 月、固定 +8 与迁移幂等；`tests/test_frontend_time_format.py` 覆盖四种时间字符串。

## 指标口径要点

- **投递成功率** = `sent / (sent + failed)`，`pending` 不计入分母；没有完成样本时显示 `—`。
- **失败记录无时间戳**：`created_at` 上线前的历史失败行无法按窗口统计，单独显示为「另有 N 条」，不会被当成当前窗口的失败。
- **逾期**：即时队列 `push_after` 已到但仍是 `pending`。静默时段、时间窗、渠道异常都会自然产生短暂逾期，持续增长才需要处理。
- **最久等待**：队列里最老一条 `pending` 的年龄，用于判断积压是否在恶化。
- **数据源新鲜度**：开启的采集源超过 24 小时没有 `last_collected_at` 即计为 stale。
- **未确认告警**：`acked_at IS NULL AND resolved_at IS NULL` 的 `CRITICAL` / `ERROR` / `WARNING`，`INFO` 不参与未确认统计；已解决事件即使未读也不再计入。
- **推送 / 成功率 KPI**：与投递统计共用全局 `hours` 窗口，切换右上角时间后同步变化。
- **今日口径**：页面不再展示独立「今日概览」，推送和产品更新统一跟随全局窗口。接口 `today` 保留给现有 Prometheus 今日指标，固定统计 CST 当天 00:00 至当前时刻；推送按 `created_at`（空值回退 `sent_at`），产品按站点发布时间 `published_at`，无时间戳与未来时间不计入。
- **产品更新**：`updates` 按 `snapshots.product_name`（产品大类）分组；`published_at` 入库时已由站点 CST 转为 UTC，窗口按 UTC `datetime('now')` 比较，页面显示时再转回 CST。
- **客户推送**：`customers` 与投递统计共用全局 `hours` 窗口；窗口内无推送的客户仍显示并置灰沉底。成功率 = 成功 / 总数，≥95% 绿、≥80% 橙、其余红。
- **事件下钻**：点击「窗口内」数字按当前时间范围过滤；点击「未确认」数字打开全部时间的未读事件（严重度按行传入），弹窗内可切换状态（未读 / 已读未解决 / 已解决）。
- **批量确认 / 批量解决**：批量确认只标记当前严重度 + 时间范围内未读的事件；批量解决只标记同一范围内未解决的事件（`POST /api/system/events/resolve-all`），二者都不会连带处理筛选范围外或已处于目标状态的事件；单条操作用行内「已读」/「解决」按钮。
- **日志异常事件去重与自愈**：`log_scanner` 的 5 分钟去重键为 `error_type + keyword + 上下文哈希`，同一行同时出现在 `app.log` 与 `service_error.log` 时只生成一条事件；无上下文时才回退到「日志文件 + 类型 + 关键词」。删除 Session 时同步按 `resolved_by='auto'` 解决该 `sid` 的「过期」事件，避免已不存在的 Session 长期占用未解决告警。
- **Session 可用性**：采集/发现可用数沿用池选择的 `purpose` + `status='active'` 条件，实际采集前仍会预检；总数包含污染状态。心跳过期/污染/错误但仍 active 的行独立标为心跳异常，并非仅凭 `expires_at` 判过期。没有活跃采集 Session 时提示到 Session 页处理。
- **采集操作与耗时**：「立即采集」必须确认，采集进行中按钮禁用；服务运行时间与本轮采集耗时分开显示，完成后通过统一导航返回首页。
- **采集失败聚合**：`_collect_quick` / `_collect_full` 按产品累计 `urls_total` 与 `url_failures`；某产品本轮有 URL 请求失败、且失败数 ≥ 成功页面数（或成功页面为 0）时，汇总为一条产品级错误写入 `collection_summary.errors`，本轮严重度升为 WARNING，而不是只留逐条 WARNING 日志。单个 URL 偶发超时仍不打断该产品其余页面；`_progress.errors` 也会并入本轮汇总，避免「采集进行中」与「采集完成」两处口径不一致。
- **服务重启**：确认后调用 `POST /api/system/restart`，只支持固定 `nsfocus-monitor.service` 的 systemd 受管进程；先核验 MainPID 等于当前 PID，再延迟提交 `systemctl --no-block restart`。非受管实例返回 409，无法查询或安排任务返回 503，成功响应只表示请求已接受。开发/验收不能实际重启生产。
- **数据库写**：`database` 来自 `src/models/database.py` 的 `write_stats()`，统计进程内所有 `execute` / `execute_rowcount` / `executemany`。计数（写操作、失败、队列超时、SQLite 超时）自本次启动累计，重启清零；分位数只覆盖最近 1024 次写，样本不足时显示 `—`。写队列（进程内 `RLock`）与 SQLite `busy_timeout` 共用 10 秒等待预算，`lock_wait_ms` 是排队时间、`sqlite_ms` 是 SQL 执行时间、`total_ms` 是两者合计；区分二者才能判断瓶颈是本进程并发还是外部连接/长事务占锁。合计 p95 ≥ 1 秒时标红，与后端 `db_write` 慢写告警同口径。日志只记录耗时与结果，不记录 SQL 与参数值。Prometheus 输出 `nsfocus_db_write_operations`、`nsfocus_db_write_errors`、`nsfocus_db_write_timeouts{reason="python_lock"|"sqlite_busy"}`、`nsfocus_db_write_timeout_rate`、`nsfocus_db_write_wait_budget_seconds`、`nsfocus_db_write_samples{scope="count"|"limit"}` 与 `nsfocus_db_write_{lock_wait,sqlite,total}_ms{quantile="p50"|"p95"|"p99"}`（无样本为 `NaN`）。
- **维护模式**：`maintenance.enabled` 读取 `system_settings.maintenance_mode`；开启时页顶显示橙色告警条，采集健康中标注「已开启（推送静默）」，Prometheus 输出 `nsfocus_maintenance_mode`。
- **站点可用性**：`nsfocus_site_check` 每 5 分钟请求 `https://update.nsfocus.com/`，HTTP 状态码 `< 500` 视为可用；5xx、超时、DNS/连接错误视为不可用并累加连续失败次数。仅在状态变化时写 `site_unavailable`（ERROR）或 `site_recovered`（INFO）系统事件，持续故障不会每轮刷屏。结果持久化在 `system_settings.site_status`，重启后仍可展示。Prometheus 输出 `nsfocus_site_up`、`nsfocus_site_http_status`、`nsfocus_site_latency_ms`、`nsfocus_site_consecutive_failures`、`nsfocus_site_last_check_age_minutes`。每轮探测同时写入 `site_probe_history`（保留 30 天）；`GET /api/metrics` 的 `site.history` / `site.history_summary` 跟随全局 `hours` 窗口，超过 180 个采样时按时间桶平均降采样，失败桶保留 `s=down` / `ms=null`，页面据此绘制延时曲线与红色失败标记。
- **CVE 情报**：与「产品更新」同排展示；卡片顶部为严重度/未评分/评分覆盖，折线趋势紧随其下（单列排布），再往下是 Top CVE。Top CVE 与明细弹窗显示 CVE 编号、中文漏洞名称和 CNVD 编号外链；名称优先取 `cve_meta.name_zh`，其次 `description_zh`，最后回退 NVD 英文 `description_en`，都没有时显示「名称待同步」；搜索框同时匹配 CVE 编号、CNVD 编号、中英文名称、文件名和版本。只统计 `status='active'` 快照的 `description_raw`（采集数据页与采集器不变）；窗口按 `snapshots.published_at`、为空回退 `first_seen_at`，UTC 比较、页面显示 CST。卡片与弹窗共用 `/api/cve/summary` / `/api/cve/list`，`rejected` CVE 不展示。文案固定为「关联 CVE」，表示描述中提到，不等同于本次修复。评分由 `nsfocus_cve_meta` 每 5 分钟按 NVD API 2.0 补齐：CVSS v4.0 → v3.1 → v3.0 → v2 取 Primary 指标，无 key 每轮最多 5 条、有 `MONITOR_NVD_API_KEY` 每轮最多 20 条；`not_found` 7 天后重试，`error` 按 10/30/120/360/1440 分钟退避，超时/连接错误/5xx/无效 JSON 属 NVD 临时故障、15 分钟后重试并结束本轮；403/429 立即结束本轮。这类预期外部网络错误不进入日志异常事件（`log_scanner` 忽略 `monitor.cve_meta` 的单条 fetch failed / rate limited），避免事件中心被外部抖动刷屏。失败只更新退避字段，不清空已拿到的评分。中文名称与 CNVD 编号由 `nsfocus_cnvd_import` 每 60 分钟读取 `MONITOR_CNVD_DIR`（默认 `data/cnvd/`）下的 CNVD/CNNVD 导出文件补齐；CNVD 公开站点有反爬挑战，系统不抓取网页，只消费管理员放入的官方导出文件。每日 03:00 清理同时删除已不存在快照的 `snapshot_cve` / `cve_scan_state` 孤儿行。
- **调度器状态**：顶部 KPI 直接显示 已启用 / 采集中 / 已关闭；关闭时 KPI 转红并在页顶显示红色告警条。
- **调度任务状态**：卡片始终列出十三个任务（采集、心跳、汇总、投递队列、清理、渠道体检、站点可用性、数据库备份、数据库健康、CVE 提取、CVE 全量重扫、CVE 评分同步、CNVD 导入），状态只通过圆点颜色表达：绿「运行中」/ 红「已停止」/ 灰「未启用」，圆点带 `title` 可悬停查看文字；被单独关闭的心跳/渠道体检等显示灰点。
- **调度倒计时**：`seconds_until <= 0` 显示「即将运行」，已停止/未启用的任务显示 `—`。

## 接入 Prometheus / Grafana

JSON 与 Prometheus 文本是同一份数据：

```bash
# 登录态读取（页面使用的方式）
curl -H "Authorization: Bearer <JWT>" \
  "http://127.0.0.1:9999/api/metrics?hours=24"

# Prometheus 文本
curl -H "X-Metrics-Token: <token>" \
  "http://127.0.0.1:9999/api/metrics?format=prometheus&hours=24"

# 或使用 Prometheus 原生 authorization.credentials_file 的 Bearer 形式
curl -H "Authorization: Bearer <token>" \
  "http://127.0.0.1:9999/api/metrics?format=prometheus&hours=24"
```

Prometheus 抓取建议配置静态令牌：

```yaml
scrape_configs:
  - job_name: nsfocus-monitor
    metrics_path: /api/metrics
    params:
      format: [prometheus]
      hours: ['24']
    static_configs:
      - targets: ['127.0.0.1:9999']
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/nsfocus-metrics-token
```

服务端环境变量 `MONITOR_METRICS_TOKEN` 未设置时，静态令牌路径关闭，只接受登录 JWT；设置后 `X-Metrics-Token` 与 `Authorization: Bearer <token>` 两种形式都接受。页面只展示抓取地址和接入说明，不读取、不保存、不展示该令牌。
